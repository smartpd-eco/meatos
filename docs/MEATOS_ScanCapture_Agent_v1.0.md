# MEATOS 스캔 캡처 에이전트 (Scan Capture Agent) v1.0 설계서

작성일: 2026-07-24
목적: **닫힌 POS를 건드리지 않고**, 계산대에서 바코드가 "찍히는 순간"을 잡아 **재고를 자동 출고(OUT)** 한다.
핵심 원리: 바코드 스캐너는 대부분 **키보드처럼 입력(HID 키보드)** 하므로, POS 소프트웨어가 아니라 **스캐너 입력 자체**를 잡으면 어떤 POS든 무관하게 동작한다.

---

## 0. 한 줄 요약

**라벨 발행(소분/준비) ≠ 판매. 판매는 계산대 스캐너가 찍히는 순간이다.**
그 순간의 스캔값만 가로채(POS와 동시에) MEATOS로 보내면, **POS 무침습 · 실시간 · 정확한 자동 출고**가 된다.

---

## 1. 왜 이 방식인가 (문제 정의)

| 순간 | 무엇 | 재고 의미 |
|---|---|---|
| 소분/준비 | 저울로 무게 달아 **라벨 발행** → 진열 | 아직 내 재고 (판매 아님) |
| **판매** | 계산대에서 **바코드 스캔 → 계산** | **이때 진짜 출고** |

- 저울(소분)과 계산대 스캐너(판매)는 **물리적으로 분리**되어 있다 → 계산대 스캐너 신호 = **순수 판매 신호**.
- POS DB는 닫혀 있어도, **스캐너 키 입력은 OS 레벨에서 잡을 수 있다** → POS 종류와 무관.

---

## 2. 아키텍처 / 데이터 흐름

```
[저울] 소분·라벨발행 ── (판매 아님, 캡처 안 함)

[계산대 바코드 스캐너]
        │  (HID 키보드 입력: 바코드 + Enter)
        ├────────────▶ 기존 POS (그대로 계산)        ← POS 무침습
        │
        └──(동시)──▶ MEATOS 캡처 에이전트 (POS PC 백그라운드)
                          │  1) 계산대 스캐너 장치만 선별 (Raw Input device 식별)
                          │  2) 바코드 파싱 (품목코드 + 내장 중량/금액)
                          │  3) 중복 방지(디바운스)
                          ▼
                     MEATOS 수신부 (Supabase REST / Edge Function)
                          │  product_barcode 매핑으로 품목 확정
                          ▼
                 inventory_movement OUT (재고 자동 차감)
                     + sales_record (STORE 채널 매출)
                          ▼
              재고·유통기한·대시보드 실시간 반영
```

핵심: **스캐너 입력은 POS로도 가고 MEATOS로도 간다(복제).** POS 동작은 전혀 바뀌지 않는다.

---

## 3. 캡처 방식 3가지 (환경별)

| 방식 | 대상 | 설명 | 범용성 |
|---|---|---|---|
| **A. 키보드-웨지 후킹** | Windows POS + HID 스캐너 | OS Raw Input으로 스캐너 키입력 복제. **가장 범용** | ★★★★★ |
| **B. 시리얼/OPOS 분기** | 스캐너가 RS-232/OPOS | 시리얼 포트 공유(Y스플리터/가상포트)로 신호 복제 | ★★★☆☆ |
| **C. Android POS 접근성** | 안드로이드 POS 태블릿 | 접근성 서비스/스캐너 브로드캐스트 수신 | ★★★☆☆ |

> 대부분의 매장은 **A(윈도우 PC + 키보드형 스캐너)** 라 A 하나로 커버된다.

---

## 4. 모든 POS에 적용 가능한가? (범용성 검토)

**결론: "Windows PC POS + 키보드형 바코드 스캐너"인 매장은 POS 브랜드와 무관하게 적용 가능하다.** 이게 국내 정육/소매의 절대다수다.

| 조건 | 적용 | 비고 |
|---|---|---|
| Windows POS + HID(키보드) 스캐너 | ✅ 가능 | 방식 A. POS 브랜드 무관(세이프POS/오케이포스/토스플레이스/포스뱅크 등 전부) |
| 스캐너가 시리얼/OPOS | ⚠️ 조건부 | 방식 B(포트 분기) 필요 |
| 안드로이드 태블릿 POS | ⚠️ 조건부 | 방식 C(별도 앱) 필요 |
| **계산대에서 바코드를 안 씀**(버튼만 눌러 계산) | ❌ 불가 | 잡을 신호 자체가 없음 → 이 매장은 실사/저울연동 등 다른 방식 |
| 저울과 계산 스캐너가 **같은 1대** 혼용 | ⚠️ 주의 | 소분/판매 구분 규칙 필요(장치·모드 분리) |

핵심 강점: **POS DB·API·벤더 협조가 전혀 필요 없다.** 스캐너라는 "공통 입력장치"를 잡기 때문에 **POS를 안 가린다.** = 여러 매장에 그대로 확장 가능(SaaS 관점 큰 무기).

한계(정직하게): 계산대에서 바코드를 안 찍는 매장, 특수 스캐너(시리얼/OPOS), 안드로이드 POS는 별도 대응이 필요하다.

---

## 5. 소분 vs 판매 오인 방지 (정확도 핵심)

- **원칙**: **계산대 스캐너 장치 1대만** 캡처 대상으로 등록(Raw Input 장치 핸들로 특정). 저울/라벨발행은 캡처 안 함 → 자동으로 "판매만" 잡힘.
- **디바운스**: 같은 바코드가 짧은 시간(예: 1.5초) 내 중복 입력되면 1건 처리(오발/중복 스캔 방지). 단, 저울 라벨은 무게가 내장돼 **패키지마다 바코드가 달라** 자연 중복 위험이 낮음.
- **미등록 바코드**: 매핑 없으면 MEATOS가 "보류(pending)"로 쌓아두고, 관리화면에서 품목 1회 지정 → 이후 자동.
- **취소/반품**: POS에서 취소해도 스캔은 이미 갔을 수 있음 → MEATOS에 **간단 취소(마지막 건 되돌리기)** 버튼 제공.

---

## 6. 구성요소

| 구성 | 역할 | 상태 |
|---|---|---|
| **캡처 에이전트**(POS PC) | 계산대 스캐너 입력 후킹 → 바코드 전송 | **신규 개발 필요** |
| **바코드 파서** | 품목코드/내장 중량·금액 해석 | 에이전트 or 서버 |
| **MEATOS 수신부** | 스캔 수신 → 품목 매핑 → OUT+매출 | **이미 있음**(inventory_movement OUT / sales_record / product_barcode) |
| **매핑 관리 UI** | 바코드↔품목 1회 등록, 보류 처리 | sell.html 재활용/확장 |
| **취소·감사 로그** | 오차 보정·추적 | 추가 |

> MEATOS 쪽 "재고 차감 로직"은 이미 만들어져 있음 → **남은 건 POS PC의 캡처 에이전트뿐.**

## 7. 액션 분담

### 👤 사장님이 할 것
1. **계산대 스캐너 정보 확인**: 스캐너가 **USB 키보드형인지**(대부분 그렇다), 계산할 때 바코드를 찍는지 확인.
2. **라벨 바코드 샘플 1개**: 실제 저울 라벨 바코드 숫자(13자리)와 그 라벨의 **실제 중량·가격** → 파서 보정용.
3. (파일럿 시) POS PC에 **에이전트 프로그램 설치** 허용(사장님 PC라 가능).
4. 미등록 품목 최초 1회 **바코드↔품목 지정**(그 이후 자동).

### 🤖 제가 할 것
1. **캡처 에이전트 설계·개발**(방식 A: Windows Raw Input 키보드-웨지 후킹, 트레이 상주).
2. **바코드 파서**(품목코드 + 내장 중량/금액) 사장님 샘플에 맞춰 확정.
3. MEATOS **수신부 연결**(스캔 → product_barcode 매핑 → 재고 OUT + 매출).
4. **매핑/보류/취소 관리 UI**(sell.html 확장).
5. **파일럿 검증**(벽산정육점) → 다매장 공통화.

---

## 8. 쿠팡이츠(배달) 채널 — 별도 처리

- **재고**: 배달 주문도 결국 "무엇이 몇 g 나갔는지" 신호만 있으면 동일하게 OUT 처리 가능(주문 항목 기반).
- **매출/정산**: 쿠팡은 **매출액 − 중개이용료 − 결제대행수수료 − 배달비 − 부가세 − 즉시할인** 등 **여러 항목이 차감**되어 정산이 복잡 → **쿠팡 판매자 데이터/정산 자료를 별도로 받아** 매출은 "채널=COUPANG"으로 분리 집계하는 게 맞음.
- 정리: **재고 차감은 스캔 신호로 통일**, **배달 매출·정산은 쿠팡 데이터로 별도** 관리.

---

## 9. 단계별 로드맵

1. **파서 확정**: 라벨 바코드 샘플로 품목코드/중량·금액 포맷 고정.
2. **에이전트 프로토타입**: POS PC 1대에서 계산대 스캐너 후킹 → 콘솔 출력 검증(POS 정상 동작 확인).
3. **MEATOS 연결**: 스캔 → 재고 OUT + 매출 자동, 실시간 반영 확인.
4. **정확도 튜닝**: 장치 선별·디바운스·취소·보류 처리.
5. **파일럿 1주 운영** → 오차(실사 대조) 점검.
6. **다매장 배포 패키지**(설치 마법사 + 원격 업데이트).

---

## 10. 리스크·주의

- **POS 동작 보호**: 에이전트는 스캐너 입력을 **읽기만(복제)** 하고 가로채지 않는다 → POS 계산은 100% 정상.
- **장치 오인**: 저울/보조 스캐너와 계산대 스캐너 구분(장치 핸들 등록)으로 해결.
- **취소·반품**: POS 취소분은 MEATOS에서 수동 취소로 보정(감사 로그 유지).
- **개인정보/보안**: 바코드·수량만 전송(고객정보 없음), 전송 암호화.
- **버튼식 POS**(바코드 미사용) 매장: 이 방식 불가 → 실사/저울연동 대체.

---

## 11. 결론

- 이 방식의 진짜 가치는 **"POS를 안 가린다"** 는 점이다. 스캐너라는 공통 입력을 잡기 때문에, **지금 나와 있는 대부분의 윈도우 POS 매장에 그대로** 넣을 수 있다 → MEATOS SaaS 확장의 결정적 무기.
- **재고 자동 출고 = 계산대 스캔 신호**로 해결(정공법). **쿠팡 배달 매출·정산은 별도** 경로.
- MEATOS 수신부는 이미 준비됨 → **남은 개발은 POS PC 캡처 에이전트 하나.** 사장님이 스캐너 샘플만 주시면 파서 확정 후 프로토타입에 착수한다.
