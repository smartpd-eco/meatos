# MEATOS OCR 엔진 분석 — 오픈소스 OCR vs LLM 비전

**작성일:** 2026-07-20
**대상:** 정육 거래명세서 인식(품목·중량·단가·공급가·이력번호 추출)
**질문:** PaddleOCR 및 다른 오픈소스 OCR을 이 프로젝트에서 쓸 수 있는가? 쓰면 속도·정확도·관련성은?

---

## 1. 지금 프로젝트에 들어와 있는 것 (현황)

| 엔진 | 통합 상태 | 실행 위치 | 현재 사용 |
|---|---|---|---|
| **PaddleOCR** (PP-OCRv5 mobile) | 코드 통합 완료 (21MB 모델 동봉) | 브라우저(WASM) | **모바일 비활성** (폰 멈춤 문제로 제외), PC 보조 |
| **Tesseract.js** (한/영) | 코드 통합 완료 | 브라우저(WASM) | 숫자 비교·보조용, 실질 미사용 |
| **EasyOCR** | 코드 경로만 존재 | **별도 Python 서버 필요** | 비활성 (`easyOcrServiceUrl` 비어 있음) |
| **Gemini 2.5/3.1 Flash Vision** | Edge Function 배포 완료 | 서버(클라우드) | **모바일 1차 (현재 주력)** |
| Upstage / Google Vision / GPT-4.1 / CLOVA | 레지스트리 stub | 클라우드 | 미연결(키·함수 필요) |

즉, **PaddleOCR와 Tesseract는 "쓸 수 있는" 상태**로 이미 들어와 있고, EasyOCR은 서버를 하나 더 띄워야 쓸 수 있습니다.

---

## 2. 핵심 개념: OCR ≠ 거래명세서 인식

거래명세서 자동화의 어려움은 "글자를 읽는 것"이 아니라 **표 구조 복원 + 필드 매핑**입니다.

- 순수 OCR(PaddleOCR·Tesseract·EasyOCR)의 출력 = **글자 + 좌표(bounding box)** 뿐.
- 여기서 다시 "이 글자는 몇 번째 행의 단가 칸" 을 맞추는 **Parser(행·열 복원)** 가 필요.
- 이 Parser가 이 프로젝트의 진짜 병목이었습니다 (인수인계서 §4.2 결론과 동일: "문자 인식보다 Parser의 행·열 복원과 필드 매핑이 핵심 병목").

**LLM 비전(Gemini)** 은 글자 인식 + 표 이해 + 필드 매핑을 **한 번에** 처리합니다. 그래서 OCR+Parser 조합이 헤매던 부분(품목명 줄바꿈 결합, 이력번호 연결, Box·중량 분리)을 바로 넘깁니다. 이것이 "관련성(적합성)"의 핵심 차이입니다.

---

## 3. 엔진별 비교 (속도 · 정확도 · 관련성)

| 항목 | PaddleOCR (브라우저) | Tesseract.js | EasyOCR (서버) | **Gemini Flash-Lite (현재)** |
|---|---|---|---|---|
| 방식 | 순수 OCR + 자체 Parser 필요 | 순수 OCR + Parser 필요 | 순수 OCR + Parser 필요 | 인식+구조화 통합(LLM) |
| **속도** | 폰: 21MB 다운로드+CPU → **수십 초~멈춤(실측)** / PC: 수 초 | 가장 느림(한글·표 약함) | 서버 GPU면 1~3초, CPU면 느림 | **실측 웜 ~3초** (콜드 4~5초) |
| **글자 정확도(한글 인쇄)** | 양호 | 낮음(한글·표 취약) | 우수(한글 강점) | 우수 |
| **표/필드 정확도(핵심)** | Parser 품질에 종속 → 불안정 | 낮음 | Parser 품질에 종속 | **높음(레이아웃 이해)** |
| **관련성(이 업무 적합도)** | 중 (무료지만 Parser 부담) | 하 | 중상 (정확하나 서버 필요) | **상 (구조화까지 한 번에)** |
| **배포·인프라** | 앱에 모델 동봉(무겁다) | 앱 동봉 | **Python 서버 상시 운영 필요** | 서버리스(이미 배포됨) |
| **비용** | $0(기기 CPU) | $0 | $0 SW + **서버 호스팅비** | **스캔당 약 2~3원** |
| **오프라인** | 가능 | 가능 | 불가(서버) | 불가(네트워크) |

> 실측 근거: Gemini flash-lite 3초·품목 6줄·중량×단가 일치 확인. PaddleOCR는 모바일에서 화면 멈춤 재현(21MB 모델·메인스레드 점유).

---

## 4. 정육 거래명세서에 대한 결론

1. **정확도·관련성 1위는 LLM 비전(Gemini).** 표·이력번호·Box/중량 분리를 코드 없이 처리 → 유지보수 부담이 가장 낮고 결과가 가장 안정적.
2. **속도도 Gemini flash-lite가 우위(~3초).** 오픈소스는 폰에서 오히려 느리고(모델 다운로드+CPU), 서버(EasyOCR)를 쓰면 빠르지만 서버를 상시 운영해야 함.
3. **오픈소스의 유일한 실익은 "API 비용 0".** 그러나 현재 단가는 스캔당 2~3원(단일 매장 월 수천 원)이라 절감액이 서버 운영비·개발 공수보다 작습니다.

**즉, 지금 규모에서는 Gemini(Flash-Lite) 1차가 속도·정확도·비용 모두에서 합리적입니다.** 오픈소스로 갈아탈 실익이 크지 않습니다.

---

## 5. 오픈소스를 쓴다면 — 언제, 어떻게 (하이브리드 안)

비용이 정말 커지거나(예: 하루 수천 장), 오프라인/보안 요구가 생기면 다음을 고려:

- **A. 무료 온디바이스 사전 필터:** PC/태블릿에서 PaddleOCR로 1차 인식 → 신뢰도 낮은 문서만 Gemini로. 폰에서는 Paddle이 무거워 부적합.
- **B. 자체 EasyOCR/PaddleOCR 서버:** 작은 GPU 서버에 OCR 서버를 띄워 API 비용 0으로 대량 처리. 단, **표 복원 Parser를 우리가 직접 고도화**해야 하고 서버 운영·장애 대응 부담이 생김.
- **C. 현행 유지(권장):** Gemini flash-lite 1차 + 사용자 검토. 비용이 문제될 때만 A/B 도입.

전환은 코드 수정 없이 가능하도록 이미 설계돼 있음: 레지스트리에 provider가 등록돼 있고, `easyOcrServiceUrl` 지정 또는 `GEMINI_VISION_MODEL` 변경으로 라우팅을 바꿀 수 있음.

---

## 6. 한 줄 요약

> "글자 읽기"는 오픈소스도 하지만, "거래명세서를 표로 이해해 필드로 뽑는 것"은 LLM 비전이 압도적. 현재 규모·단가에서는 **Gemini Flash-Lite 1차가 최적**이고, 오픈소스는 대량·오프라인 요구가 생길 때의 비용 절감 카드로 남겨둔다.
